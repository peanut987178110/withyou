# 课程生成方法说明

适用于 AI 虚拟陪伴产品 × WorkBuddy 全套课程及后续修改。

## 1. 每次制作前必须先读

先完整阅读本文，再阅读《课程制作约定.md》《产品经理方法大全.md》《AI虚拟陪伴产品_新版课程表.md》，检查 raw 全量目录与更新，结合当课主题精读相关原始资料。不能只凭历史生成内容或聊天摘要续写。用户后续明确要求优先于本文。

## 2. 核心标准：方法逻辑 + 连续案例 + 操作练习

每节课都要让学员知道：今天解决什么问题，为什么这样做，具体怎么做，产出什么，如何判断结果。

方法是教学主线；故事呈现方法的使用过程；画面帮助理解过程。避免两个极端：把方法定义扩成大段条目、反复绕圈；为了讲故事删掉方法、只讲人物经历。

丰富体现在解释、推导、案例细节、方法图表与操作结果上，不能靠堆术语或装饰。

## 3. 先确定当课问题和方法链

依据新版课程表确定本课范围、前课输入、后课衔接，避免提前讲完下一课。

先用一句话写本课核心问题，再明确学员学完能独立完成的动作和产物。按因果关系选择并排列必需方法：前一步的产物，应成为后一步的输入。

每个方法必须讲清五件事：

1. 解决什么问题？
2. 具体怎么做？
3. 案例人物怎样使用？
4. 得到什么产物？
5. 用什么标准检查？

《产品经理方法大全》是参考库，按当课需要选取，不能把整份清单塞进每课。安装课、技术课、测试课应有各自的方法链。

第四课参考链路：真实目标 → 场景与任务 → 经历访谈 → 证据分层 → 替代方案 → Agent 四问 → 需求假设 → 最小实验与判断。JTBD、MVP 在第四课只作必要铺垫，第五课系统展开，不机械套用到其他课程。

## 4. 故事短、清楚、为方法服务

围绕同一个产品、同一组人物和一个明确任务推进。故事要有起因、困难、行动和结果。

用“遇到什么问题 → 为什么采用这个方法 → 怎么使用 → 得到什么 → 如何决定下一步”的逻辑连接各段。

案例具体到人物说了什么、做了什么、看到了什么、修改了什么。不能只说“后来做了调研”，跳过方法操作。删掉无关闲聊、重复设问和反复提醒，不为制造剧情增加支线。

虚构案例必须标明。虚构访谈不构成现实调研证据；用户自述应标记为自报行为，不能当成已独立核实的事实。计划、示例和真实结果严格分开，不编造实验已经通过。

## 5. 制作顺序：先逐字稿，再 PPT

固定顺序：资料阅读 → 目标与方法链 → 连续故事 → 完整逐字稿 → 逐页视觉设计 → PPT → 双向核对。

先写完整、可直接讲课的逐字稿，再按讲稿设计画面和翻页。不能先做条目 PPT，再硬配讲稿。

页数按内容与节奏确定，不固定为 8、9 或 12 页，也不能靠砍掉方法、减少页数解决“绕”。

逐字稿要求：

- 用老师正常讲课的口语，简单直接，有因果关系。
- 开头说明本课问题和学完能完成的动作。
- 概念讲清含义、适用条件、边界；方法演示操作过程与结果。
- 从故事动作自然引出方法，并明确说出方法名称和可复用做法。
- 加入必要的对话、反例、互动和参考答案；避免每页同一模板。
- 每页讲透当前问题后向前推进；过渡说明下一步为何必要。
- 学员听完能照着做；只有故事或只有定义均不合格。
- 按实际稿件长度和练习安排估算时长，不给短稿虚标长课时。
- 结尾回收方法链，安排针对本课目标的作业，衔接下一课。
- 不附讲师附件、制作日志、无关说明或交付物清单。

最终逐字稿为纯文本，按“【第 N 页｜实际标题】”标注，与 PPT 的物理页码和标题一致。

## 6. PPT 同时还原故事和展现方法

每页确定：故事此刻发生什么、学员需要理解什么方法、什么画面最能解释。

| 内容 | 适合的视觉形式 |
| --- | --- |
| 接到任务、追问目标 | 办公室情境、人物对话、修改前后的需求草稿 |
| 用户场景 | 时间与环境、手机界面、触发事件和连续行为 |
| 访谈 | 问答、追问位置、标注后的访谈记录 |
| 证据整理 | 原话、自报行为、产品判断的对照表 |
| 替代方案 | 对比矩阵，显示满足之处和未满足之处 |
| 需求拆解、流程 | 层级图、流程图、明确的输入和输出 |
| 需求假设 | 填写完整的实例卡，突出证据、风险和待验证问题 |
| MVP、实验 | 范围比较、界面原型、实验步骤与观察记录 |
| 验证决策 | 指标口径、预设标准、结果与后续动作映射 |
| 技术实操 | 准确界面或标明的示意图、输入输出、成功与错误示例 |

人物、界面和案例前后保持一致。故事画面与方法图表组合使用，不能只在人物旁边摆条目，也不能全篇相同卡片网格。

保持深色高对比科幻风：深色背景、近白正文、青色与浅紫强调，风险可用其他强调色。保证字号、留白、安全边距、页码清晰。页面短文提示结构，完整解释交给讲稿。避免长段文字、拥挤、低对比和无意义装饰。

## 7. 概念与证据准确

- Prompt 规定模型行为；Memory 管理长期信息；RAG 检索后提供生成依据。
- Function Calling 是模型提出结构化工具请求，由应用校验和执行，不等于动作已成功。
- Workflow 组织确定执行步骤、变量、分支与失败处理。
- Skill 是按需加载的专业规程和资源；Agent 在目标与权限内选择行动；MCP 是连接工具与资源的协议。
- 不为凑内容强加技术，不把人工体验演示当成自动化能力已验证。
- 小样本访谈用于发现线索，不能直接证明市场规模或需求成立。
- 实验前确定观察对象、行为口径、时间窗口、判断标准和后续决策；示例阈值标明为教学预设，不能说成通用标准。
- 对外统一使用“AI 虚拟陪伴产品”，不出现本地项目名称。

## 8. 同源制作与逐页核对

用同一份逐页内容源维护标题、完整讲稿、画面设计、要点与练习。逐字稿和 PPT 从同源生成；讲者备注必须同步完整讲稿，不能只放摘要。

完成后逐页检查：

1. 本课问题、方法链和学习成果是否明确？
2. 每个方法是否讲清目的、做法、案例、产物和检查标准？
3. 故事是否推动方法使用，有无绕圈和无关情节？
4. PPT 是否还原关键故事动作，并清楚呈现方法结构？
5. 页数、物理页码、标题、案例、讲稿与备注是否一致？
6. 版面有无溢出、遮挡、拥挤，字号和对比度是否可读？有条件时渲染逐页查看。
7. 术语、来源、虚构标注、计划与结果是否准确？
8. 文件是否有效并保存成功？只报告实际做过的检查。

成功导出不代表教学与版式已经检查通过。

成品统一放在 F:\withyou\课程。旧版先备份到“备份”目录，避免备份重名覆盖；保存可编辑逐页内容源和生成源，便于后续修改。

## 9. 后续修改方式

每次制作或修改课程，第一步先读本文。方法不清先改方法链；讲法绕先改逐字稿；画面单薄则依据讲稿中的情节和方法补充视觉。讲稿内容变化后同步 PPT，保持一一对应。

最终要求：学员看得懂故事，学得会方法，知道下一步怎么做。
