【第 1 页｜AI 虚拟陪伴产品的完整产品地图】

大家好，欢迎来到第三课。

前两节课，我们做了两件事。

第一件事，我们讨论了为什么要做 AI 虚拟陪伴产品：不是因为模型很新，也不是因为“陪伴”听起来很有情绪价值，而是因为某些用户在某些具体时刻，确实需要一种低压力的回应、一个可以表达的空间，或者一个能够陪他完成小任务的对象。

第二件事，我们安装并跑通了 WorkBuddy，让一个最小智能体完成了第一次对话。

但到这里，我们手里还只是一个“能对话的东西”。它距离一款真正的产品，还有很长一段路。

今天我们要把镜头拉远。

不要只看聊天框里的那一句回复，而是看看一款 AI 虚拟陪伴产品究竟由什么组成：用户从哪里进入？他能做什么？哪些地方真的需要 AI？哪些地方其实只是普通的产品功能？记忆放在哪里？资料怎么被检索？外部动作怎么执行？如果一个任务有好几个步骤，谁来安排这些步骤？

今天我想用一个生活化的比喻。

如果第一课是在讨论“我们要不要开一家餐厅”，第二课是在厨房里成功做出了一道菜，那么第三课就是站到餐厅门口，看看整家餐厅怎么运转。

门口要有菜单，顾客要知道怎么点单；前台要记录订单；后厨要分工；有些菜需要固定流程，有些菜可以根据顾客需求灵活调整；食材要有库存；结账要真实完成。顾客看到的是一次用餐体验，但背后其实有很多层系统共同工作。

AI 产品也是一样。

用户看到的是页面和对话，产品背后却有 Prompt、记忆、知识库、工具、工作流、权限、数据和测试。

今天的目标不是让大家记住更多术语，而是让大家能画出一张地图。以后再遇到一个新概念，我们知道应该把它放在哪一层，也知道它到底解决什么问题。


【第 2 页｜先跟着用户走一遍】

我们先不画技术架构，先跟着一个用户走一遍。

假设有一位用户，晚上回到家，打开这款 AI 虚拟陪伴产品。

他第一次打开时，最关心的可能不是“你用了什么模型”，而是：“我现在可以做什么？”

如果首页只有一个空白输入框，他可能会有点茫然。是直接聊天？是选择角色？是做复盘？是查询记忆？还是设置提醒？

所以进入产品，是用户旅程的第一步：让用户知道从哪里开始。

接下来，他可能在聊天框里说：“今天工作特别乱。”

这时他可能有几种不同的需求。

他可能只想说说话；可能想让 AI 帮他理清今天发生了什么；可能想做一份晚间复盘；也可能只是想找一个熟悉的角色陪他待一会儿。

如果产品直接替他决定“现在开始复盘”，用户可能会觉得被安排了。更好的做法，是理解他的表达，然后给他一个选择：“我可以先听你说，也可以陪你简单整理一下今天发生的事情，你想选哪一种？”

这就进入了互动阶段：表达、选择和获得回应。

如果用户选择复盘，产品就进入任务阶段。任务可能包括提取今天发生的事件、识别用户明确表达的感受、生成一份草稿，然后让用户确认。

注意，这里的“任务”不是“多聊几句”。它应该有一个结果。

比如用户最后得到三句话：今天发生了什么、我真正介意什么、明天准备先做什么。

互动结束后，用户还会面对一个选择：要不要保存？

如果他确认保存，系统可能留下一个复盘记录；如果他不想保存，就应该真的不保存；如果他中途退出，也不应该偷偷把内容当成长期记忆。

这就是结果阶段：确认、保存、退出或再次使用。

大家会发现，这条用户旅程里已经有很多产品设计问题了，但我们还没有讲任何技术名词。

这很重要。我们先知道用户经历了什么，才知道系统需要什么。

接下来我会不断提醒大家：用户旅程不等于技术实现。用户看到的是“我点击确认”，后台可能要做权限检查、状态更新和数据库写入；用户看到的是“我选择复盘”，后台可能要启动一条工作流。

同一件事情，体验层和技术层的描述方式不一样。


【第 3 页｜用户旅程不等于技术 Workflow】

这一页专门讲一个很容易混淆的地方：体验流程、业务流程和技术 Workflow，不是一回事。

我们继续用刚才的例子。

用户看到的体验流程可能是：打开产品，输入一句话，选择“复盘”，看到问题，确认摘要，保存记录。

这描述的是用户看到了什么、做了什么选择。

业务流程则是：系统识别用户意图，启动复盘任务，提取信息，生成草稿，等待用户确认，保存记录。

它更关心产品为了完成这件事，需要经过哪些业务环节。

技术 Workflow 则要继续往下拆：

开始节点拿到什么输入？是聊天文本、会话 ID、用户 ID，还是用户选中的消息范围？

提取节点输出什么？是普通文本，还是结构化的事件列表？

校验节点检查什么？字段是否完整，信息是否来自用户明确表达，是否存在空结果？

摘要节点接收哪个变量？是原始聊天记录，还是校验后的事件列表？

用户确认如何暂停？系统是否支持等待状态？用户取消后如何结束？保存失败后如何重试？

这才是技术 Workflow 的问题。

资料里把 Workflow 比作生产线，这个比喻很准确。一条生产线不是“工人从头做到尾”，而是把不同工序按照顺序连接起来。每个工序有输入，有产出，产出再交给下一个工序。

Agent 则更像一个助理。它可以根据目标和当前情况，决定是直接回答、调用工具，还是进入某条已经设计好的 Workflow。

比如一个个人助理 Agent，可能有写周报 Workflow、写 PRD Workflow、订机票 Workflow 和设置提醒 Workflow。用户只说“帮我安排一下明天的行程”，Agent 负责判断应该调用哪条流程；一旦进入“创建日程”这条流程，具体的参数校验和执行仍然可以是确定的。

所以不要把 Workflow 理解成“所有聊天都必须画成流程图”，也不要把 Agent 理解成“完全自由，什么都让模型自己决定”。

固定流程适合确定性、权限和可验证性要求高的任务；Agent 适合意图判断、能力选择和开放式交互。实际产品里，两者经常组合使用。

用户旅程讲的是用户怎么走；业务流程讲的是产品要完成什么；技术 Workflow 讲的是系统怎样执行。

把这三个层次分开，后面我们就不容易把“用户点击了一个按钮”误说成“系统已经完成了一条工作流”。


【第 4 页｜一款 AI 产品的四层结构】

现在我们把整款产品拆成四层：体验层、能力层、执行层和数据层。

先看体验层。

体验层是用户能直接看到的东西：Home 页面、聊天页面、记忆页面、按钮、弹窗、加载状态、成功提示和错误提示。

比如用户点击“确认记忆”，按钮变成“已保存”，这属于体验层。

第二层是能力层。

这里放的是产品能够做什么：Prompt 让模型按某种方式回应；Memory 让系统管理用户长期信息；RAG 让系统从资料里找到依据；Skill 提供一套专业操作规程；Tool 让系统可以获取外部信息或执行动作。

第三层是执行层。

执行层负责把事情真正跑起来，包括 Workflow、状态、权限、分支、重试、异常和调用顺序。

用户点击“确认记忆”后，执行层要判断：这个用户是不是当前账号？这条记忆是不是当前用户的？请求是不是重复提交？版本有没有冲突？

第四层是数据层。

用户信息、会话消息、候选记忆、已确认记忆、复盘记录、任务记录、工具调用日志和产品指标，都属于数据层。

我们用一个看似简单的动作串一下。

用户确认：“我最近在准备考试。”

页面上出现一个确认按钮，这是体验层。

前端把请求发给后端，后端校验身份和记忆版本，这是执行层。

数据从 proposed 变成 confirmed，这是数据层。

以后用户再次说“最近有点累”，系统读取这条已确认信息，让模型在合适时机承接，这是能力层。

一个按钮，穿过了四层。

这就是为什么做 AI 产品不能只盯着模型回复。一个功能失败，可能是页面没有发送请求，可能是权限拒绝，可能是数据没保存，也可能是模型没有正确使用信息。

产品经理如果能把问题定位到层，沟通效率会高很多。


【第 5 页｜页面功能和 AI 能力不是一回事】

这一页要解决一个很常见的误区：页面上出现的每个功能，都不等于 AI 功能。

登录、注册、导航、页面跳转、设置、列表、弹窗，这些很多是普通产品能力。

它们当然重要，但不需要因为产品名字里有“AI”，就把它们都包装成 AI。

理解用户意图、生成自然语言回应，是模型能力。

例如用户说：“我不想复盘，只想随便聊聊。”系统要理解他改变了意图，这可能需要模型或规则共同判断。

检索资料、查询日程、读取数据库、调用外部服务，是连接能力。

保存状态、校验权限、删除数据、处理并发，是系统和数据能力。

我们看四个失败案例。

第一个，用户点击“删除记忆”，但页面刷新后记忆还在。这首先不是 Prompt 问题，而是接口、状态或数据删除问题。

第二个，用户说“帮我做复盘”，模型却开始讲一段大道理。这可能是 Prompt、上下文或意图判断问题。

第三个，用户问自己之前保存的放松清单，模型回答了一堆清单里没有的内容。这要检查 RAG 检索和生成约束。

第四个，模型回复“提醒已经创建”，但日历里根本没有提醒。这要查 Function Calling 的调用请求、应用校验、真实执行结果和回传链路。

如果所有问题都被叫作“模型不行”，团队就没有办法定位。

产品地图的价值之一，就是给问题分配正确的归属。


【第 6 页｜把技术概念放回产品地图】

现在我们把几个核心概念放回四层地图里。

Prompt 规定模型怎么回应。它可以规定角色、任务、语气、边界、示例和输出格式。

Memory 管理用户长期信息。重点不是“让 AI 永远记住一切”，而是信息是否经过确认，如何更新，如何删除，如何隔离不同用户。

RAG 是先检索资料，再把相关内容交给模型生成。它适合资料多、需要依据或需要追溯来源的场景。RAG 的效果取决于资料、切分、检索、排序和生成约束，不是接一个向量库就结束。

Function Calling 是模型提出结构化的工具请求。例如模型请求调用 create_reminder，并给出时间和标题参数。真正的函数由应用校验并执行，成功或失败的真实结果再回给模型。

Skill 是按需加载的专业操作规程和资源包。比如晚间复盘 Skill 可以包含触发描述、执行步骤、输出模板和验证规则。它告诉 Agent 或流程“应该怎么做”，但它本身不等于一张正在运行的节点图。

Workflow 是确定的多步骤执行流程。它负责输入、输出、变量、节点顺序、分支、循环、失败和结束。

我们还可以补一句 Agent。

Agent 是在目标、上下文和权限约束下，选择下一步行动的系统。它可能直接回答，也可能检索、调用工具，或者进入某条 Workflow。

这些概念可以组合，但职责不能混。

例如一个 Agent 识别出用户想做晚间复盘，加载相关 Skill，选择复盘 Workflow；Workflow 中的某个节点再通过 Function Calling 请求保存记录；外部服务也可能通过 MCP 连接。

这不是让所有概念同时出现，而是让每个概念在真正需要时承担自己的责任。


【第 7 页｜同一条晚间复盘需求，穿过四层系统】

我们现在完整走一遍。

用户输入：“陪我做一次复盘。”

体验层先给回应和选择：开始复盘，还是先聊几句？

能力层开始工作。Prompt 规定如何承接和追问；Memory 读取已确认的偏好，比如用户不喜欢一次被问很多问题；Skill 提供晚间复盘的操作规程；如果用户要求参考过去保存的资料，RAG 负责检索。

执行层启动 Workflow。

第一节点拿到选中的聊天内容和当前用户身份。第二节点提取事件和明确表达的感受。第三节点校验结果：有没有内容？是否把猜测当成事实？第四节点生成复盘草稿。第五步把草稿交给用户确认。

这里特别要注意“等待用户确认”。

如果产品只是画一个“等待”节点，但运行环境没有真正的暂停和恢复能力，那它并没有实现确认。确认可能意味着一次新的请求、一个任务状态，或者一套可恢复的会话机制。

用户点击确认后，保存节点才把记录写入数据层。保存失败时，页面要显示真实错误；用户取消时，流程要结束；用户重复点击时，要避免重复保存。

最后，数据层留下的是一条真实的复盘记录和对应状态。下次用户回来时，系统能区分已确认内容、本次草稿和普通聊天上下文。

大家看，这已经不只是“AI 回复得温柔不温柔”。它是页面、模型、规程、流程、数据和权限共同完成的一次产品体验。


【第 8 页｜V0.1 的功能地图要敢于留白】

现在我们做范围控制。

V0.1 先做单人、单伴侣、文字对话、稳定回应、可控记忆和一个轻量任务。

轻量任务可以是晚间复盘，也可以是明日小计划，但最好先选一个，不要两个都做得很浅。

复杂语音、主动来电、商城、订阅、成长系统可以暂缓。暂缓不是说这些能力永远没有价值，而是先把核心价值验证清楚。

每一项功能都要补三句话。

第一，它解决哪个用户问题？

第二，它依赖哪些能力和系统？

第三，怎样算完成？

比如“晚间复盘”解决的是用户想把一天整理清楚的问题；它依赖 Prompt、Skill、Workflow、可能的 Memory 和数据存储；验收标准包括：用户可以启动，信息不足时能补充，中途可以退出，草稿需要用户确认，保存结果真实存在。

如果一个功能只是因为“行业里别人都有”，但说不清用户问题，就先放到待定区。

产品地图不是越满越专业。

一张有留白、能执行、能验收的地图，通常比一张塞满名词的地图更有价值。


【第 9 页｜今天的作业：画出第一张产品地图】

今天的作业不需要写一份大而全的 PRD。

先画五个页面入口：Home、Chat、Memory、Skills、Settings。

再标出三个 AI 能力。可以是 Prompt、Memory、RAG，也可以根据你的产品方向替换。

然后写出两个数据或外部动作来源，比如用户资料、数据库、日历或提醒服务。

接着选一条核心用户旅程，写清楚四件事：用户输入什么，系统处理什么，用户看到什么结果，哪些内容会被保存。

最后写一张 V0.1 暂不做清单。

作业的重点不是画得漂亮，而是每个框都能回答三个问题：用户为什么需要它？系统怎么完成它？完成后怎么验收？

今天我们完成了从“一个聊天产品”到“一个完整 AI 产品”的第一次扩展。

我们看了用户旅程，也区分了体验流程、业务流程和技术 Workflow；看了体验层、能力层、执行层和数据层；把 Prompt、Memory、RAG、Function Calling、Skill 和 Workflow 放回了正确位置。

下一课，我们会从这张产品地图进入更具体的需求分析和页面状态，把“我想做一个陪伴产品”继续拆成能实现、能测试的产品需求。

先把今天的地图画出来，再开始堆功能。谢谢大家，我们下一课见。
